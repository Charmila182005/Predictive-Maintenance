## 1. Project objective

Create a production-oriented predictive-maintenance system that accepts machine operating data and produces:

- Overall machine-failure probability
- Predicted failure class
- Machine-health status
- Anomaly score
- Ranked likely failure modes
- Supporting condition evidence
- Important contributing features
- Risk and urgency level
- Recommended maintenance action
- Model version and prediction timestamp

The primary manual and programmatic inputs are:

- Product Type: L, M, or H
- Air Temperature in K
- Process Temperature in K
- Rotational Speed in rpm
- Torque in Nm
- Tool Wear in minutes

Calculate these derived features:

- `temperature_difference = process_temperature - air_temperature`
- `mechanical_power_w = torque * rotational_speed * 2 * pi / 60`
- `overstrain_measure = tool_wear * torque`

## 5. Targets and leakage prevention

Use `Machine failure` as the main binary target.

Treat the following as failure-mode targets:

- `TWF`: Tool Wear Failure
- `HDF`: Heat Dissipation Failure
- `PWF`: Power Failure
- `OSF`: Overstrain Failure
- `RNF`: Random Failure

Remove identifiers such as `UDI` and `Product ID` from model inputs.

Never use `Machine failure`, `TWF`, `HDF`, `PWF`, `OSF`, or `RNF` as prediction features. When training any target, exclude every target-label column from its feature matrix.

Use only information that would be available at prediction time. Add an automated leakage test that fails if an identifier or target column enters a model’s predictors.

## 7. Condition engine

Implement the dataset-specific AI4I condition calculations separately from the ML models:

### Heat Dissipation Failure evidence

```text
temperature_difference < 8.6 K
AND rotational_speed < 1380 rpm
```

### Power Failure evidence

```text
mechanical_power_w < 3500 W
OR mechanical_power_w > 9000 W
```

### Overstrain Failure evidence

```text
Product Type L: overstrain_measure > 11000
Product Type M: overstrain_measure > 12000
Product Type H: overstrain_measure > 13000
```

### Tool Wear Failure evidence

Tool Wear Failure is associated with the dataset-generation wear interval, but do not present an arbitrary deterministic cutoff as a universal factory rule.

### Random Failure

Do not force a sensor-based explanation for RNF because its generation is random.

Return triggered rules and measured values as supporting evidence. Describe them as AI4I-specific conditions unless they have been calibrated and approved for the target factory.

## 15. Time-related prediction limitation

The AI4I dataset consists of synthetic observations and does not provide a dependable timestamped run-to-failure sequence or defined future prediction horizon.

Therefore:

- Do not claim “failure in the next X hours.”
- Do not call the output remaining useful life.
- Describe the result as failure risk under the supplied operating condition.
- If true early-warning or remaining-useful-life prediction is required, find an appropriate official time-series run-to-failure dataset and build it as a clearly separate model.
- Never mix a time-series dataset into AI4I without documenting machine identity, temporal ordering, target definition, and domain differences.
